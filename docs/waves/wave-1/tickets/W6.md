## HOW ANALYTICS RUN
Each tool calls `const cache = await ctx.cache.ensure([...feeds it needs])`, computes from `cache.rows(feed)`, and returns `asTool(summary, buildResult({...}))` from common.ts. Pure computation lives in `src/analytics/<name>.ts` as functions taking `(cache: CacheReader, args, now)` so tests can call them with `test/helpers/fake-cache.ts` directly. Tests for the tool wrappers can pass a fake `ctx.cache` via `connect(...)` only if trivial; prefer testing the pure functions thoroughly.

## GOAL: tools in src/toolsets/analytics.ts (export `analyticsTools`, all read; core where marked)
1. `sc_safety_pulse` (core): period (default "last 7 days") vs previous equal period, optional site_ids. Metrics with deltas: inspections completed, average score, failed-item rate (failed items / scored or answered items), new issues, actions created vs completed, open overdue actions (count + oldest age), missed scheduled occurrences (if the schedules feed has data). Delta direction is only stated when both periods have >= 20 observations; otherwise "too few to compare". Output also three `attention` items chosen by a documented severity rule (overdue high-priority action > missed occurrence on a template > failed-rate jump of >= 10 percentage points > new high-priority issue), each with a record id/link.
2. `sc_analyze_failed_items` (core): text query (case-insensitive, `|` for alternatives) on item label and response, template_ids, site_ids, period (inspection completion date), group_by item|template|site|inspector, top N. Pareto table: group, failed count, share, cumulative share, failure rate (failed / times the item was answered), example inspection ids (max 3). Identity of an item across template versions = normalised label + template.
3. `sc_analyze_action_backlog` (core): site_ids, priority, group_by site|assignee|priority|label, overdue_only. Open-action ageing buckets 0-7 / 8-30 / 31-90 / 90+ days (from created), overdue buckets (from due date), open with no due date counted separately; resolution time (created -> completed) median and p90 for actions completed in the period; opened vs closed per week for the period; oldest 10 open actions. Use the actions feed and action_assignees feed for assignee grouping.
4. `sc_analyze_schedule_compliance` (core): period, site_ids, template_ids, group_by schedule|site|assignee|template. From schedule occurrences: due, completed on time, completed late, missed, upcoming/pending; compliance % = on time / (due and resolved); late counted separately; worst 10. If the occurrences feed is empty, return a clear "no scheduling data" result, never zeros presented as compliance.
5. `sc_analyze_credential_radar` (core): horizon (default "next 30 days" via parsePeriod), credential type filter, include_expired (default true). Buckets: expired, <= 7 days, <= 30 days, <= 90 days, beyond horizon excluded; group by person and by credential type; join users for names. If the credentials feed is empty, say so.
6. `sc_analyze_site_league`: period, min_inspections (default 10), metrics: inspections, average score, failed-item rate, open overdue actions per site, action median resolution days; rank by a documented composite (z-scores, equal weights, configurable list of metrics); sites below min volume listed separately with reason; rank change vs previous period.
7. `sc_analyze_compare_periods` / site comparison in one tool `sc_analyze_compare`: compare two periods OR two site groups on failed-item rate (two-proportion test), average inspection score and action resolution time (Mann-Whitney), with verdicts from stats.ts ("real difference" / "probably noise" / "not enough data"), effect sizes and plain-English explanation. Note in caveats that repeated inspections of the same site are not independent.

Every result: summary sentence quoting the key numbers and record counts; `method` explains the formula in one or two sentences; caveats from coverage plus tool-specific ones (for example "lower issue counts can mean less reporting, not fewer hazards").
